# Варианты: добавление новостей и редакционного контента

**Новость** здесь — материал редакции: анонс, обзор, рекомендация («куда сходить»), не парсинг СМИ. Целевая таблица: `editorial_posts` (+ подборки `curated_lists`).

---

## Что уже заложено в модели

```sql
editorial_posts (
  city_id, shop_id?, author_user_id?,
  slug, title, body, cover_media_url,
  is_published, published_at
)
```

**Нет в схеме (пока):** `post_type`, `linked_entity_type/id`, `excerpt`, `tags[]`, `seo_title`. Их можно добавить миграцией или обойтись без них на MVP.

Публичный read: RLS `is_published = true`. Write-политик для редакции **нет** — запись только service role / SQL.

---

## Вариант A — Supabase Studio / SQL (как сейчас)

**Суть:** редактор или разработчик вручную вставляет строки в `editorial_posts` и `curated_list_items` через Supabase Dashboard или миграции/seed.

| Плюсы | Минусы |
|-------|--------|
| Нулевая разработка UI | Нужен доступ к БД, риск ошибок |
| Быстрый старт для 10–20 постов | Нет превью, slug, расписания публикации |
| Уже работает с текущими миграциями | Не масштабируется на 3–5 постов в день |

**Когда брать:** первые 2–4 недели после запуска витрины, пока нет страницы `/guides/[slug]`.

**Минимальный чеклист публикации:**

1. `city_id` = Улан-Удэ  
2. Уникальный `slug` (латиница, `otkrylas-kofeynya-x`)  
3. `body` — HTML или Markdown (договориться один формат)  
4. `is_published = true`, `published_at = now()`  
5. Опционально `shop_id` → `inuu-editorial`

## Вариант B — Dashboard INUU для роли «Редакция»

**Суть:** раздел в `pages/dashboard/` (или отдельный `pages/editorial/`) для `shop` с `org_type = editorial` / роли `city_editor`.

**Экраны:**

- Список постов (черновик / опубликован / архив)
- Редактор: заголовок, slug (авто из title), обложка (Storage), body (Tiptap / Markdown)
- Привязки: venue / event / provider (поля или блок «связанные сущности»)
- Кнопки: «Сохранить черновик», «Опубликовать», «Снять с публикации»

**API (Nitro):**

- `POST/PUT/DELETE /api/dashboard/editorial/posts`
- Проверка: пользователь — member `shop_id` редакции или platform admin
- Загрузка медиа: паттерн как `dashboard/stories/media.upload`

| Плюсы | Минусы |
|-------|--------|
| Единая экосистема с событиями и stories | 1–2 недели разработки |
| RLS + аудит по `author_user_id` | Нужен WYSIWYG и валидация slug |
| Публикация → webhook в TG-канал (этап 2) | |

**Когда брать:** цель 3–5 материалов в неделю от редакции без участия разработчика.

## Вариант C — Внешняя CMS + синхронизация

**Суть:** писать в Notion, Sanity, Strapi, Directus; cron или webhook пишет в `editorial_posts`.

| Плюсы | Минусы |
|-------|--------|
| Удобный редактор для нетехнарей | Второй источник правды |
| Версии, черновики, медиатека из коробки | Синхронизация slug, city_id, связей |
| Можно отдать SMM без доступа к prod БД | Задержка публикации, отладка сложнее |

**Подварианты:**

| CMS | Интеграция | Заметка |
|-----|------------|---------|
| Notion | API → Nitro job | Дёшево для старта, слабый SEO-контроль |
| Sanity / Strapi | Webhook on publish | Норм для долгой редакции |
| Google Docs + скрипт | Экспорт MD → seed | Только прототип |

**Когда брать:** редакция уже живёт в Notion и не хочет новый интерфейс.

## Вариант D — Markdown / JSON в репозитории

**Суть:** файлы `content/ulan-ude/news/*.md` с frontmatter; при деплое или по кнопке «импорт» — upsert в Supabase.

| Плюсы | Минусы |
|-------|--------|
| Git-история, review в PR | Редакции неудобно без Git |
| Легко тестировать на preview | Нет «опубликовать сейчас» без деплоя |
| Хорошо для SEO-шаблонов | |

**Когда брать:** мало авторов, сильная связка контент ↔ релиз кода (редко для INUU).

---

## Вариант E — Telegram-бот (редакция + партнёры + модерация)

**Суть:** один бот — два потока:

1. **Редакция:** `/news`, `/event` → черновик → сразу публикация.
2. **Партнёры:** `/submit` → очередь `content_submissions` → в **чат менеджеров** кнопки ✅ Принять / ❌ Отклонить / ✏️ На доработку.

Полная спека: **[04-telegram-bot-content-moderation.md](./04-telegram-bot-content-moderation.md)**. В коде уже есть аналог — модерация UGC фестиваля (`festivalUgcModeration.ts`).

| Плюсы | Минусы |
|-------|--------|
| Редакция и партнёры уже в TG | Длинные тексты неудобны |
| Модерация без отдельного dashboard на старте | ~1–1.5 нед разработки |
| Inline-кнопки как у заказов/UGC | Нужен групповой чат + whitelist редакторов |

**Когда брать:** партнёры шлют заявки в DM/TG; менеджеры хотят принимать в одном чате. Dashboard — позже для правок и SEO.

---

## Вариант F — Не отдельные посты, а только подборки + stories

**Суть:** не вести ленту статей; весь редакционный контент — `curated_lists` + `story_campaigns` + короткие описания на `venues.editorial_quote`.

| Плюсы | Минусы |
|-------|--------|
| Минимум сущностей | Слабый SEO, нет архива «новостей» |
| Быстрее MVP афиши | Обзоры «на 2000 знаков» некуда |

**Когда брать:** pivot «только подборка на выходные» (см. roadmap, развилка 1).

## Связь новости с другими сущностями

| Подход | Описание |
|--------|----------|
| **F1. Поля в `editorial_posts`** | `linked_entity_type`, `linked_entity_id` (enum как `inuu_entity_type`) |
| **F2. Ссылки в body** | В HTML/Markdown вручную `/ulan-ude/events/foo` |
| **F3. Только подборка** | Новость = item в `curated_list_items` с `note` |
| **F4. Дубль как event** | Анонс МК и как `editorial_post`, и как `events` — риск рассинхрона |

**Рекомендация для MVP:** F1 (одна связь) или F3 для подборок; для МК — см. [02-masterclasses-events-options.md](./02-masterclasses-events-options.md).

## Типы материалов vs хранение

| Тип (из verticals) | Где хранить |
|--------------------|-------------|
| Короткая новость | `editorial_posts` |
| Подборка «Топ-5» | `curated_lists` + items |
| Обзор после МК | `editorial_posts` + ссылка на `event` |
| Афиша месяца | `curated_list` или PDF в Storage + пост-анонс |

Опциональная колонка `post_type enum ('news','review','guide','announcement')` — упростит фильтры на `/ulan-ude/news`.
